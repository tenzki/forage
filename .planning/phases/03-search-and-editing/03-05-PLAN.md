  <name>Task 1: Add FTS5 backfill to migration</name>
  <files>src-tauri/migrations/0002_search_and_editing.sql</files>
  <action>
Add the FTS5 backfill statement AFTER the three sync triggers (INSERT, DELETE, UPDATE) and BEFORE the undo_history section. The statement populates the FTS5 index with all pre-existing rows:

```sql
-- Backfill FTS5 index with any rows that existed before this migration
INSERT INTO nodes_fts(rowid, content_text) SELECT rowid, content_text FROM nodes;
```

This is needed because FTS5 external content mode does NOT auto-index existing rows -- only the triggers fire for new/updated/deleted rows going forward. Without this backfill, any node created before migration 0002 is invisible to search.

IMPORTANT: After modifying the migration file, the user's existing database already has the old schema applied. The executor must ALSO create a one-time backfill that runs at app startup or as a Rust command. The simplest approach: in the Rust database initialization code (likely `db.rs` or `lib.rs`), after running migrations, execute the backfill SQL directly:
```sql
INSERT OR IGNORE INTO nodes_fts(rowid, content_text) SELECT rowid, content_text FROM nodes WHERE rowid NOT IN (SELECT rowid FROM nodes_fts);
```
Actually, FTS5 tables don't support `rowid NOT IN` queries. Instead, the safest approach is to rebuild the entire FTS5 index:
```sql
INSERT INTO nodes_fts(nodes_fts) VALUES('rebuild');
```
Add this `rebuild` command after migrations run in the Rust DB init. The FTS5 `rebuild` command re-reads all rows from the content table and re-indexes them. It is idempotent and safe to run on every startup (fast for small datasets).

Find the Rust file that runs migrations (likely src-tauri/src/db.rs or similar) and add the rebuild statement after the migrate!() call.

FIX B -- Record pending flush in undo() before calling undoStepIpc (treeStore.ts):
In the `undo` action (around line 785-805), replace the code that discards the flush result. Instead, when flush() returns a pending group, record it via recordUndoStepIpc BEFORE calling undoStepIpc. The fix:

```typescript
undo: async () => {
  // Flush any pending text edit group and RECORD it before undoing
  const pending = undoTracker.flush()
  if (pending) {
    const prevNodeId = pending.startSnapshot as { id?: string }
    const nodeIdForGroup = prevNodeId?.id ?? ''
    if (nodeIdForGroup) {
      // Get the current node content as the "after" snapshot
      const currentNode = findNodeById(get().nodes, nodeIdForGroup)
      if (currentNode) {
        try {
          await recordUndoStepIpc(
            'text_edit',
            nodeIdForGroup,
            JSON.stringify(pending.startSnapshot),
            JSON.stringify({ id: currentNode.id, content: currentNode.content }),
            pending.groupKey
          )
        } catch (e) {
          console.warn('Failed to record pending undo group:', e)
        }
      }
    }
  }

  try {
    const result = await undoStepIpc()
    if (result && result.node_ids.length > 0) {
      await get().loadTree()
    }
  } catch (e) {
    console.error('Failed to undo:', e)
  }
},
```

The key change: instead of discarding the flush result, we capture the current node state as after_json and call recordUndoStepIpc. This ensures the active typing session is recorded to the undo_history table before undoStepIpc attempts to step backward.
